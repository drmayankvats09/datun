# ADR-0005: Content Security Policy — Nonce-Only Architecture

**Status:** Accepted.
**Date:** May 14, 2026.
**Deciders:** CTO (Mayank Vats).
**Supersedes:** ADR-0004 (Strict CSP with Hybrid Nonce/Hash Architecture).
**Superseded by:** None.

## Context

ADR-0004 adopted a hybrid Content Security Policy: marketing and legal pages
were classified as "static" and received a hash-based CSP, while authenticated
routes received a nonce-based CSP. The hash registry (`inline-hashes.ts`,
generated by `scripts/build-inline-hashes.ts`) covered the inline
`<script type="application/ld+json">` blocks on the five static pages.

During the Phase 2 report-only soak, the browser console on `/en` reported
thirteen `Executing inline script violates CSP` errors. Investigation
established the root cause:

1. Next.js App Router emits its own inline bootstrap scripts
   (`self.__next_f.push(...)` streaming-RSC chunks) on **every** page,
   static or not. These are executable scripts, not JSON-LD.
2. On a hash-classified route these framework scripts carry no nonce, their
   SHA-256 hashes are not in the registry, and `'strict-dynamic'` causes the
   browser to ignore the host allowlist. Every framework script was therefore
   blocked under report-only and would break hydration under enforce.
3. The framework scripts' content changes per build and per page, so
   pinning them by hash is not maintainable.
4. Separately, the JSON-LD blocks the hash registry was built for are
   `type="application/ld+json"` — non-executable data. Browsers never run
   them, so `script-src` never evaluates them. The hash registry was
   protecting scripts that did not need protection.

In short: the hybrid model's "static" branch was both broken (for the
framework scripts it failed to cover) and unnecessary (for the JSON-LD
scripts it did cover).

## Decision

Remove the hash branch entirely. **Every HTML route receives a nonce-based
CSP.** A per-request 128-bit nonce is generated in `apps/web/proxy.ts` for
all routes; `apps/web/lib/csp/policy.ts` emits `script-src 'self'
'strict-dynamic' 'nonce-...'`. Next.js automatically applies the nonce to
every framework `<script>` it renders — the mechanism it officially
supports and the one already proven in production on authenticated routes.

Removed:

- `apps/web/lib/csp/route-classification.ts` — there is no longer a
  static/dynamic distinction for CSP purposes.
- `apps/web/lib/csp/inline-hashes.ts` and
  `apps/web/scripts/build-inline-hashes.ts` — the hash registry and its
  build step.
- The `build:hashes` and `prebuild` scripts in `apps/web/package.json`.
- The duplicated `stableJson()` helper in the five pages that carry inline
  JSON-LD — those `<script type="application/ld+json">` blocks need no
  deterministic serialization because they are never hashed.

Unchanged:

- `'strict-dynamic'`, the hard-block directives, the allowed-origins
  single-source-of-truth, the dual `report-to` / `report-uri` reporting,
  and the `Reporting-Endpoints` header.
- The `report-only` → `enforce` mode flip remains a single
  `NEXT_PUBLIC_CSP_MODE` environment-variable change.

## Alternatives Considered

### Alternative A: Extend the hash registry to cover Next.js framework scripts

Hash every `self.__next_f.push(...)` chunk at build time.

**Rejected because:** the content of these chunks is the serialized RSC
payload — it changes on every content edit and every build, and there are
many chunks per page. The registry would be perpetually stale. This is
fighting the framework.

### Alternative B: Keep the hybrid model, accept the violations in report-only only

Never advance the static pages to enforce mode.

**Rejected because:** it leaves the highest-traffic pages permanently
without enforced XSS protection, defeating the purpose of Task #45.

### Alternative C: Add `'unsafe-inline'` to static-route `script-src`

**Rejected because:** `'unsafe-inline'` provides no XSS protection. This is
the configuration Task #45 exists to eliminate.

## Consequences

### Positive

- One CSP mechanism, one mental model. No build-time hash registry to keep
  in sync; no "this helper must be byte-identical across six files"
  invariant.
- The landing page and legal pages can finally advance to enforce mode —
  the Phase 3 goal.
- Next.js's own nonce propagation is the supported, documented path; the
  application stops fighting the framework.
- Net deletion of code: two library modules, one build script, two test
  files, two `package.json` scripts, and a duplicated helper across five
  pages.

### Negative

- The landing page and the four legal pages are now dynamically rendered
  rather than statically generated, because emitting a per-request nonce
  requires per-request rendering. At Datun's current scale (pre-launch,
  ~100 users, the landing page is a single-viewport "Coming Soon" screen)
  the lost edge-cache benefit is immaterial; the homepage already executes
  middleware on every request for locale detection. This trade-off should
  be revisited if and when a high-traffic static surface (e.g. the Task #97
  clinic-SEO pages) ships — at that point a per-route exception, or
  Next.js's evolving static-CSP support, can be evaluated.

### Neutral

- ADR-0004's three-phase rollout (build → report-only → enforce) still
  stands. This change is a correction applied within the report-only phase,
  followed by a fresh soak before the enforce flip.
